# CR-04 师生端交互成对校验规范（Interaction-Pairing Review）

> 版本：v1.0 ｜ 触发：2026-08 实机测试发现两处"学生端有提示、教师端无操作"断链（CR-05）
> 定位：CR-01 §6.5 的执行细则。**凡是会出现在学生/教师屏幕上的文案或状态，都必须是"成对"的。**

---

## 1. 什么是"交互成对"（成对不变量）

本系统是**双端协同**架构：教师的操作由学生端响应，学生的诉求靠教师端处理。任何一端出现"文案"而另一端没有对应操作，就是断链：

```
学生端提示（toast / hero / 空态 / 错误）──(必须)──▶ 教师端处理入口（按钮 / 告警 / 状态）
   可感知，可理解                      可达：按阶段可见
   指向正确动作                        完整：真的能解决，而非报错
```

> 成对校验问的是三件事：**对应**（有这个入口吗）、**可达**（该阶段能看到吗）、**完整**（点了能解决吗）。

## 2. 审查触发与流程

| 触发 | 必做动作 |
|------|----------|
| PR 含学生端 renderer/views.js、downlink.js、student 端文案改动 | 逐条提取新增提示 → 填矩阵 §4 → 确认教师端入口 |
| PR 含教师端新操作（按钮/接口/告警） | 反向确认学生端有可感知反馈（toast/状态切换/指令） |
| PR 改状态机/阶段流转 | 用 UX-01 §6.1 剧本重走一遍受影响旅程 |
| 版本发布前 | 全量跑一遍 CR-04 §4 矩阵 + `scripts/verify-pairing.js` |

**角色**：作者在 PR 描述附"交互成对自查表"；主审必须逐行核验矩阵中的"闭环验证场景"是否成立；把关人对任何"只有提示、没有操作"的改动行使一票否决。

## 3. 必查规则（红线）

1. **提示必有解**：学生端任何引导"请老师/举手/联系老师/等待老师"的文案，教师端必须存在真实可达操作；
2. **操作必有感**：教师端任何针对学生机的动作，学生端必须收到可感知结果（哪怕只是 toast/状态切换）；
3. **前后端规则同源**：控件可见阶段与服务端放行阶段一致，不允许"能点但必被拒"（CR-02 R-1 / UX-02 U-4 教训）；
4. **文案与能力同步改**：能力改完，引导文案同步更新（本次已把"请举手"升级为"请举手，老师会为你撤销关机"）。
