# 代码审查标准与流程（Code Review Standard & Workflow）

> ⚠ **已取代（2026-09-06）**：本文件 v1.0 已并入《审查标准总纲 v2.0》并引入改动风险分级 C0~C3。此后一切审查以总纲为准，本文件仅存档。

> 版本：v1.0 ｜ 适用：ALL SCOPE 课堂管理系统（三端 + shared + 交付包）及团队后续所有代码
> 制定：代码审查专家（2026-09-06）｜ 状态：已被 v2.0 取代

---

## 1. 目的与适用范围

代码审查是**质量闸门**，不是"找茬"。本规范的目标：

1. 保证合入主线的代码满足正确性、安全性、可维护性底线；
2. 让每一次审查都成为**知识传递**——作者与审查者双向成长；
3. 把团队已有的好实践（见 §6.3"团队红线"）固化为**全员默认行为**，而非某个人的个人习惯。

适用范围：`classroom-mgmt/{teacher,student,preset-studio,shared}`、`scripts/`、交付包配置，以及任何新增源码文件。
审查对象是**合入变更**（diff），发布前另做全量走查（见 §4.4）。

## 2. 审查原则（五条铁律）

| # | 原则 | 含义 |
|---|------|------|
| P1 | 对事不对人 | 讨论代码，不评判作者；"这段逻辑"而非"你写的"。 |
| P2 | 每条意见可执行 | 说清**位置 + 问题 + 为什么 + 改法**。只说"这里不好"等于没说。 |
| P3 | 分级不刷屏 | 🔴 阻断 / 🟡 应改 / 💭 建议，宁可少而准，不可多而噪。 |
| P4 | 先赞后批 | 好的设计（幂等、状态机、边界守卫）要点名表扬，好行为才会被复制。 |
| P5 | 一次审完 | 审查者一次给全意见，禁止挤牙膏式分批评论。 |

## 3. 问题严重度分级

| 级别 | 标记 | 定义 | 处置 |
|------|------|------|------|
| **阻断** | 🔴 | 合入会造成：安全漏洞、数据丢失/损坏、不可恢复的运行时故障、破坏对外契约、违反合规 | **必须修复后方可合入**；由把关人确认关闭 |
| **应改** | 🟡 | 边界输入未校验、明显性能隐患、代码/注释不一致（潜伏 bug 信号）、缺失关键测试、重复代码 | 建议本 PR 修复；无法立即修须**建 Issue 跟踪**，把关人同意后方可放行 |
| **建议** | 💭 | 风格不一致、命名优化、文档补充、替代方案探讨 | 作者自行决定，不计入合入门禁 |

> 判定口诀：会不会**崩**（🔴）？会不会**错**（🟡）？还是只是**不够好**（💭）？

## 4. 审查时机与类型

### 4.1 提交前自检（作者，~5 分钟，必做）
合入前作者跑一遍《CR-03 提交前自检清单》：
- 单元/冒烟测试过：`cd classroom-mgmt && bash run-tests.sh`（按变更范围决定 `--full`）；
- 命中质量门禁：单文件 ≤300 行（db 仓储/存储 ≤320）、无 emoji、无硬编码色、按钮 ≥80px；
- diff 自读一遍：删除的调试代码、遗留 TODO/FIXME、`console.log` 是否清理。

### 4.2 PR 审查（日常主流程）
1. 作者开 PR：标题 = 变更摘要，描述按模板（见 CR-03 §A）；
2. 指定 ≥1 名主审 + 1 名把关人（把关人通常为模块 Owner）；
3. 审查者按 §6 清单审 **diff**，评论分级标注；
4. 🔴 全关闭、🟡 全处理或挂单后，把关人 Approve；
5. 作者合入；**合入者 ≠ 作者本人**（4 眼原则）。

**规模控制**：单 PR 建议 ≤400 行 diff。超出则拆分为多个逻辑独立的 PR。
审查时限：24 小时内首评（团队内约定，避免阻塞迭代）。

### 4.3 紧急修复（hotfix）
线上/课堂事故修复可先合入后补审，但必须：
- 在 PR 描述标注 `[hotfix]` 与事故链接；
- 24 小时内补审，发现的问题转 Issue。

### 4.4 发布前全量走查（版本基线）
对齐现有《真机测试前自检结果清单》的做法，每版本发布前做一次：
- 全量源码走查 + `run-tests.sh --full` + 交付包一致性核验；
- 本次（v4.2）已执行一轮，问题见《CR-02 实际审查报告》。

### 4.5 专项审计（按需）
涉及安全敏感变更（关机链路、HMAC、鉴权、导入导出、MQTT 协议）时，触发专项审计，审查者须包含安全视角，必要时对照 §6.4 安全清单逐条过。

## 5. 角色与责任

| 角色 | 责任 | 禁止 |
|------|------|------|
| 作者 | 自检、开 PR、回应每条评论、修复 🔴/🟡 | 自我 Approve、静默合入带 🔴 的 PR |
| 主审 | 通读 diff、按清单给分级意见、讲解原因 | 只点赞不挑错（"LGTM"党）、刷屏无价值评论 |
| 把关人（Owner） | 裁决争议、确认 🔴 关闭、放行合入 | 未核验就 Approve（Trust but verify） |
| 全员 | 每周小结会上分享 1 个"本周最有价值的审查发现" | —— |

## 6. 审查清单

### 6.1 通用维度（每 PR 必过）
- [ ] **正确性**：边界值（0/负数/超长/空/null）？状态机非法迁移？时间/时区处理？
- [ ] **安全**：输入校验在**服务端**而非只在前端？拼接进 HTML/CSV/SQL/命令的数据是否净化？
- [ ] **可维护**：命名表意？函数单一职责？注释解释"为什么"而非"是什么"？
- [ ] **性能**：循环内查库（N+1）？全表扫描能落索引/白名单过滤？大对象每次全量传输？
- [ ] **测试**：核心行为有测试？本次变更的"快乐路径 + 至少一条异常路径"覆盖？
- [ ] **错误处理**：关键路径失败有兜底？异常是否会被静默吞掉且无日志？
- [ ] **契约**：shared/topics.js 等共享契约是否双端同步修改？openapi.yaml 是否同步？

### 6.2 按层补充清单

**服务端（teacher/src）**
- [ ] 路由层薄、服务层承载业务；HTTP 入参做了服务端兜底校验（参考 `startSession` 座位 1-99/分组 1-20 的双端校验模式）
- [ ] 写库用 db 仓储接口；批量写走 `transaction`；事件 `msg_id` 幂等与业务写**同事务**
- [ ] 新增表/列：storage-sql.js `TABLES/PK/DDL/_migrate` 四处置于一致；JSON 降级后端同接口可用
- [ ] 定时器类逻辑：进程重启后能**恢复重挂**（吸取 CR-02 S-1 教训）或明确降级策略

**MQTT 链路（bridge/handlers）**
- [ ] 越界座位忽略（`seatInRange`）、未知 type 忽略、单条坏消息不打断消息流
- [ ] 前置校验先于 `insertEvent`（防毒丸 msg_id）
- [ ] SSE 广播在事务提交后

**前端/渲染（public / renderer）**
- [ ] 所有用户可控数据入 `innerHTML` 前过 `esc()`（防 XSS）；属性上下文注意引号转义
- [ ] 表单提交有乐观置位与失败回滚；按钮尺寸/无硬编码色符合门禁

**Electron 主进程（student/main.js、preset-studio/electron）**
- [ ] 渲染层不可信：仅白名单 IPC；secret/fs/child_process 不进 preload
- [ ] 关机/敏感操作由主进程终裁（校验与执行尽量原子，见 CR-02 S-3）

**数据导出（export）**
- [ ] 导出单元格数据做公式注入净化（`= + - @` 前缀处理，见 CR-02 S-2）
- [ ] 文件名/exportId 防路径穿越白名单

### 6.3 团队红线与惯用法（源自代码走查沉淀，全员默认遵守）
| 红线 | 理由 |
|------|------|
| SQL 一律参数化 + 列白名单；禁止字符串拼 SQL | 注入防护（现有 SqlStorage 模式） |
| HMAC_SECRET / broker 口令不得使用占位默认值上线 | 学生端已有强制 dry-run，教师端需同样闸门（CR-02 S-4） |
| 座位范围、信封 type、任务状态值先校验后落库 | 防幻影数据/污染统计 |
| 共享契约禁止各端复制，只改 `shared/` 单一真源 | 双端 diff 失步是事故源头 |
| 物理主题切换只改 topics.js（TOPIC_PLAN） | 切 Plan 一处生效 |
| 状态机迁移必须走 `ALLOWED` 表，禁止裸 update phase | 阶段单向不可回退是业务不变量 |
| `catch(_e){}` 必须带注释说明为何可吞 | 裸吞异常是 bug 温床 |

### 6.4 安全专项清单（专项审计/敏感变更用）
- [ ] 鉴权是否默认开启或至少**默认拒绝**？（CR-02 R-1）
- [ ] 服务监听地址是否最小暴露（非 0.0.0.0 或配防火墙）？
- [ ] CORS 是否白名单化而非 `app.use(cors())` 全开？
- [ ] 密钥比较用 `crypto.timingSafeEqual`
- [ ] 导出的学生数据（姓名/学号）是否有泄露面（日志/API/CSV）
- [ ] 关机链路的"校验+执行"是否可被渲染层绕过（参考 S-3）

### 6.5 师生端交互成对校验（必查项，v4.2.1 起强制执行）
改动若**新增或修改学生端提示文案/状态页/两端交互**，作者与审查者必须逐条回答"学生看到这条提示后，老师在哪个入口处理？"，规则详见《CR-04 师生端交互成对校验规范》：

- [ ] 学生端每条提示（toast/hero/空态/错误文案）→ 教师端存在**对应、可达（按阶段可见）、完整（能真正解决）**的操作入口？
- [ ] 反向：教师端每个单座/全局操作 → 学生端有**明确可感知**的结果反馈？
- [ ] 两端共用的动作/状态词查术语词表（UX-01 §8）唯一？
- [ ] 前后端规则一致：控件可见阶段 = 服务端放行阶段（参考 CR-02 R-1 / UX-02 U-4）？
- [ ] 交互闭环回归：`node classroom-mgmt/scripts/verify-pairing.js` 通过？
- [ ] CR-04 交互矩阵对应行已更新为"闭环"？

## 7. 合入完成定义（Definition of Done）

一个 PR 满足以下全部条件才可合入：
1. 无未关闭 🔴；🟡 全部处理或已建 Issue 跟踪；
2. `run-tests.sh` 通过（按范围选择 full），无回归；
3. 命中质量门禁；无调试残留；
4. 共享契约/API 文档（openapi.yaml、03/04 文档）同步更新；
5. 把关人 Approve 且合入者 ≠ 作者。

## 8. 度量与复盘（轻量，不搞报表工程）

| 指标 | 口径 | 目标 |
|------|------|------|
| 审查覆盖率 | 已审查 PR / 全部 PR | 100% |
| 缺陷逃逸率 | 发布后 2 周内发现的 🔴/🟡 / 该版本审查总数 | < 10% |
| 平均首评时长 | PR 创建 → 首条评论 | ≤ 24h |
| 单 PR 🔴 数 | —— | 0（有则复盘根因） |

每周例会 5 分钟：过一遍本周 🔴 与"最有价值审查发现"；每迭代回顾一次流程是否有效。

## 9. 生效与迭代

- 本规范经团队评审通过后生效，试行 2 个迭代；
- 试行期结束由全员投票修订；任何红线变更须记录在案（本文件历史区）。
