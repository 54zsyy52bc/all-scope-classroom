# UX 审查标准与流程（Usability Review Standard & Workflow）

> 版本：v1.0 ｜ 适用：ALL SCOPE 课堂管理系统三端界面与用户旅程
> 定位：与《CR-01 代码审查标准与流程》**并行的独立审查线**——代码审查回答"对不对、稳不稳"，UX 审查回答"顺不顺、懂不懂、怕不怕"。
> 制定：代码审查专家（2026-09-06）｜ 状态：待评审生效

---

## 1. 为什么需要独立的 UX 审查

代码审查通过 ≠ 用户旅程通顺。本项目的用户是**初二学生与任课教师**（其中一个是未成年人、一个是教学场景下"眼睛在教室不在屏幕"的人），UX 缺陷的代价不是小摩擦而是**课堂节奏被打断**：

- 老师口头说"把任务做了"，学生屏上却显示"活动已截止" → 术语漂移制造的即时困惑；
- 教师误以为"课中"也能强制关机，点了却被拒绝并看到 `E-OFF-01 … task` → 信任损伤；
- 学生看到"第 1 步 / 共 3 步"却找不到第 2、3 步 → 对界面叙事失去信任。

这些 bug 无法被单元测试发现，只能靠**结构化的人因走查**。本规范把这类走查制度化，与功能测试互为补充。

## 2. UX 审查原则

| # | 原则 | 含义 |
|---|------|------|
| U-P1 | 站在用户旅程上审查 | 不审查"页面好不好看"，审查"任务能不能顺畅做完"：从开机到关机的整条链路。 |
| U-P2 | 术语即契约 | 用户看到的每个词都必须是全系统唯一的；漂移 = 缺陷，不靠"大家习惯了"豁免。 |
| U-P3 | 状态可见 > 功能存在 | 功能做了但用户不知道在哪个状态、下一步是什么、为什么被禁用 = 等于没有。 |
| U-P4 | 防误触与容错优先 | 危险动作要"可预见后果"；失败要"可理解原因 + 可执行下一步"。 |
| U-P5 | 以初二学生为基准 | 文案、步数、术语都按"12-13 岁、零培训、可能紧张"校准；教师端按"投屏/远距离/忙碌"校准。 |

## 3. UX 问题严重度分级（与代码审查同构）

| 级别 | 标记 | 定义（UX 语境） | 处置 |
|------|------|-----------------|------|
| **阻断** | 🔴 | 用户在无外部帮助下**无法完成任务**（旅程中断、流程死锁、误导导致错误操作且不可逆） | 必须修复后上线 |
| **应改** | 🟡 | 任务可完成但**强困惑/强摩擦**：术语冲突、误导性反馈、无意义的步骤信息、可见却被拒绝的操作 | 本迭代修复或建 Issue |
| **建议** | 💭 | 轻微摩擦、文案打磨、视觉/无障碍增强 | 作者自定，进 backlog |

> 代码审查问"会不会崩"；UX 审查问"**会不会卡住、会不会误解、会不会点错**"。

## 4. 审查时机与类型

| 时机 | 触发条件 | 方法与产出 |
|------|----------|-----------|
| **界面变更 PR 自查** | 任何改动用户可见文案/布局/流程 | 作者按 §7 最小自查清单逐条过；UI 术语改动须同步词表（§8） |
| **UX 走查（Walkthrough）** | 新增页面/流程、阶段流转变化、v4.x 级功能 | 按 §6 剧本模板走查 ≥2 条主流程 + 1 条异常流程；非作者执行 |
| **发布前 UX 审计** | 版本基线（配合现有全量自检） | 全三端走查 + 术语词表 grep 一致性扫描（机器可查，见 §9） |
| **专项 UX 审计** | 面向学生/教师的关键旅程重构 | 需 ≥1 名"非作者 + 具低龄用户同理心"评审；可安排 1-2 名学生/新教师试跑 |

## 5. 角色

| 角色 | 责任 |
|------|------|
| 作者 | 自查清单、提供走查所需前置条件（进入哪个状态、数据如何造） |
| UX 走查员 | 至少 1 名非作者；以目标用户视角执行剧本；只记事实不辩解 |
| 把关人 | 裁决 🟡、确认 🔴 关闭、维护术语词表 |

> 关键约束：**作者不得自审自己的 UX**（人对自己的设计"已经知道答案"，看不见困惑）。

## 6. UX 走查方法：剧本 + 启发式双轨

### 6.1 场景剧本（每剧本一页，逐条记录）
剧本字段：**起点状态 → 操作步骤（照实点）→ 每一步的"预期/实际" → 用户能否说出"我现在在哪、下一步做什么" → 问题与级别**。

内置剧本（版本基线必须覆盖，可扩展）：
1. **一节课闭环（教师）**：待课 → 开始上课（选班级/活动预设）→ 观察登记 → 发布活动（预设模板）→ 计时暂停/调时长/重计时 → 下课 → 归还全部 → 关机。
2. **一节课闭环（学生）**：开机待课 → 自动进入登记 → 填姓名座位 → 勾器材数量 → 提交锁屏 → 任务三态上报 → 归还勾选 → 确认。
3. **异常路径**：① 断线重连（学生端应可见"未连接"+ 恢复自动回位）；② 座位冲突（大屏红色告警 + 教师复位）；③ 锁定策略切换（学生端锁屏原因可读）；④ 预设包导入坏包（预演阶段报错可理解）。

### 6.2 启发式检查面（每面 ≥3 个采样点）
- **状态可见性**：当前阶段、连接、等待原因、操作是否已生效（禁用原因要写明）。
- **一致性与标准**：术语、阶段名、按钮动作名、状态色（accent/危险/求助）语义全系统一致。
- **防误与容错**：危险操作有后果预览与二次确认；失败提示 = 原因 + 下一步，不是裸错误码。
- **反馈即时性**：提交后有无乐观反馈；离线提交有明确告知；重复点击有防抖提示。
- **文案可读性**：无内部 token（errorCode/英文原语/技术缩写）直出；placeholder 具体可模仿。
- **可达性基础**：键盘可聚焦（模态首字段自动聚焦）、触屏目标 ≥80px、`aria-pressed/role=dialog` 语义、对比度（深色大屏投影场景）。

## 7. 界面变更 PR 最小 UX 自查清单（作者）

- [ ] 本 PR 是否引入/改动用户可见**文案**？涉及的概念在词表（§8）中是否唯一？改动是否同步到三端对应文案？
- [ ] 是否有**用户可见状态**变化（新阶段/新禁用条件）？用户能否知道"为什么"？
- [ ] 新增/修改**表单或确认框**：是否避免原生 prompt/confirm？校验失败是否有行内可读提示而非静默？
- [ ] 危险操作（关机/重置/删除/下课/结束）是否有后果说明？
- [ ] 错误场景是否做了**用户语言**处理（中文、无 errorCode、含下一步）？
- [ ] 目标人群校准：初二学生 3 秒能懂吗？教师投屏 3 米能看清关键态吗？

## 8. 术语词表（UX 契约，唯一真源）

> 新增/修改界面文案前先查词表；发现漂移立即修或在此登记"拟统一"。目前词表初版与审查发现见《UX-02 报告》§三词表建议，评审后固化于此。

**词表登记规范**：概念 → 对外唯一词 → 已废弃说法（禁止出现在新文案）→ 涉及文件清单。
（初版由 UX-02 提供：核心争议词对「任务 / 活动」「上课 / 开始上课」「SIoT 在线 / 已连接」等。）

## 9. 可机器化的 UX 检查（低成本常驻）

| 检查 | 手段 | 频率 |
|------|------|------|
| 术语漂移扫描 | grep 对 词表"禁止说法"在三端 renderer/public 文案中的计数 | 每次发布前 |
| 原生弹窗扫描 | grep `window.confirm/prompt/alert`（应为 0，替换为自定义组件） | CI 门禁候选 |
| 错误码直出扫描 | grep `errorCode` 拼接进 toast 的代码路径 | 每次发布前 |
| 按钮/触控尺寸 | 现有质量门禁（≥80px）已覆盖 | 已生效 |

## 10. UX 完成定义（DoD-UX）

用户可见变更满足：① 无未关闭 🔴；② 🟡 已处理或挂 Issue；③ 新文案过词表；④ 无原生弹窗新引入；⑤ 主流程剧本走过一遍（非作者）。

## 11. 与代码审查的关系

同一 PR 可同时挂两类审查：代码审查管正确/安全/性能，UX 审查管旅程/术语/反馈。两者问题可以互为线索——例如 CR-02 R-1 的"按钮可见却必被拒"本质是 UX 与业务规则不一致（UX-02 U-4），修代码时一并处理文案。
