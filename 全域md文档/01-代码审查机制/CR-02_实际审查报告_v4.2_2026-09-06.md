亮点（精读中反复出现的好实践，已固化为 CR-01 §6.3 红线）：

## 二、🔴 阻断问题

### R-1 教师端 HTTP API 默认无鉴权 + CORS 全开 + 监听 0.0.0.0 —— 学生机可跨域驱动管理接口

**位置**：`teacher/server.js:66-68`（`app.use(cors())` 无白名单 + `requireAuth` 挂在 `/api/v1`）、`teacher/src/config.js:39-40`（`ENABLE_AUTH:false`、`TEACHER_TOKEN:''`）、`teacher/src/config.js:32`（`HTTP_HOST:'0.0.0.0'`）、`teacher/app-config.json`

**为什么（攻击链）**：
- 教师端监听全网卡，学生机与教师机同处教室局域网 → 学生机可达 `http://<教师机IP>:3000/api/v1/...`；
- `ENABLE_AUTH:false` → 所有写接口裸奔：`POST /sessions/:id/phase`（推进/关闭课堂阶段）、`POST /commands/reset`、`POST /sessions/:id/policy`、`POST /sessions/:id/activities` 等（`routes/session.js:48`、`routes/command.js`、`routes/activity.js`）；
- `app.use(cors())` 全开 → **学生机浏览器里任意网页**（不限于学生机本地程序）都能跨域 fetch 上述接口；
- 读接口还暴露全班**姓名/学号/座位**隐私数据（`GET /sessions/:id/students`）。

即：一个调皮的学生在浏览器地址栏开个 F12 或打开任意带恶意脚本的网页，就能读取全班隐私、把课堂推进到 return/closed 破坏上课。（关机指令受服务端阶段+归还闸门双重保护，暂不能直接越权触发——这是唯一幸存的防线。）

**建议（按成本从低到高，建议全做）**：
1. 默认值翻转：`ENABLE_AUTH: true`，首次启动自动生成随机 `TEACHER_TOKEN` 写入 app-config 并提示教师；大屏前端登录页持有 token（同源 localStorage 即可）。
2. CORS 白名单化：仅允许教师机本机来源/指定端口，替换裸 `cors()`。
3. `HTTP_HOST` 默认绑教师机实际 IP 或 `127.0.0.1`（大屏同机访问）；如需学生机访问特定资源，走明确白名单路由。
4. 交付说明中把"上线前必须设 ENABLE_AUTH=true + 修改默认凭据"列为**发布检查项**（并入《真机测试前自检清单》C 节）。

## 三、🟡 应改问题

### S-1 活动计时截止定时器进程重启后丢失，且代码注释与实现矛盾

**位置**：`teacher/src/services/activity.service.js:20-21, 41-49, 116, 194`（`timers` 为进程内 Map；`armTimer` 仅在"发布活动/计时控制"两处调用）；`teacher/server.js:95-104`（`start()` 无恢复扫描）

**为什么**：注释声称"教师端服务重启后…截止检测重新开始"，但**没有任何引导期逻辑**重挂 running 任务的到期定时器。教师端若在上课中途重启（杀进程重开/断电恢复，DB 持久化使 `t_task` 仍为 `running`）：到期提醒不再触发、`expireTask` 不执行、依赖"无 running 活动→锁定"的策略判定（`policy.service.js:59` 仍视其为 running）会使学生机在非活动期**保持解锁**，且无任何告警。属静默失效。

**建议**：`server.js start()`（或 `wire()`）后追加 `restoreTimers()`：查当前会话中 `timed=1 AND timer_state='running'` 的任务，用 `taskSvc.remainingMs` 重挂 `armTimer`；为超过 `durationSec` 的任务直接置 `expired` 并走策略重算。补一条对应测试（模拟重启后到期触发）。

### S-2 导出 CSV 未做公式注入净化（CSV Injection）

**位置**：`teacher/src/services/export.service.js:90-92`（`csvOf` 用 `Papa.unparse` 无 transform）、`:31-46`（`buildStudents` 含用户可控的 `name/studentNo`）、`:48-59`（`buildTasks` 含标题/说明）、`:76-86`（`buildEvents` 含 payload 明细）

**为什么**：学生姓名/学号、活动标题为**用户输入**。若某值以 `=、+、-、@、\t、\r` 开头（恶意学生可轻易在登记页姓名栏输入，或直接构造 MQTT 信封），生成的 CSV 被教师在 Excel/WPS 打开时会把该单元格解析为**公式执行**（经典载荷 `=HYPERLINK(...)`、`=cmd|'/c calc'!A0` 等），造成公式注入/潜在数据外泄。系统特意为 CSV 加 BOM 以适配 Excel，恰好放大了该风险面。

**建议**：`csvOf` 内对每个字符串单元格做净化——首字符为 `= + - @ \t \r` 时前缀加 `'`（Excel 约定）或前置半角空格；写一行 `sanitizeCell()` 并配套单测（用例：`=1+1`、`@sum`、`-2+3`、正常姓名不受影响）。

### S-3 学生端关机"校验"与"执行"拆分两个 IPC，渲染层成为决策点

**位置**：`student/main.js:209-210`（`shutdown:verify` 与 `shutdown:execute` 两个独立 handler）、`student/preload.js:57-64`、`student/renderer/downlink.js:133-148`

**为什么**：主进程正确持有 secret 并做 HMAC+时间窗校验，但**校验通过与否由渲染层决定是否调用 execute**。若渲染层被攻破（如后续引入远程内容/加载了被污染页面），攻击者可直接 `executeShutdown` 绕过校验（当前 `dryRun` 默认 true 是最后防线，一旦部署者按文档关闭 dryRun 即失效）。安全设计原则：决策不应交给不可信层。

**建议**：合并为单一原子 IPC `shutdown:request(ticket, opts)`，在主进程内完成"验签 → 时间窗 → 是否 dry-run → 执行"，渲染层只传票据。preload 仅暴露这一个通道，从 API 面上杜绝绕过。

### S-4 教师端对占位默认凭据无强制闸门（学生端有，教师端没有）

**位置**：`teacher/src/config.js:25-26`（`HMAC_SECRET:'change-me-before-deploy'`、`SIOT_PASS:'dfrobot'` 硬编码默认）、`teacher/app-config.json`；对照 `student/main.js:111-113,126-129`（占位 secret → 拒绝执行/强制 dry-run）

**为什么**：关机 HMAC 与 broker 登录均依赖默认口令的"没人改"。学生端已有占位值强制 dry-run 的保护设计，但教师端**缺同类闸门**——`sendShutdown`（`command.service.js:35`）会用占位 secret 正常签发 HMAC 令牌，任何能读到代码/配置默认值的人（交付包内的 app-config）都可伪造关机票据。两端的保护强度不一致。

**建议**：教师端 `server.js` 启动时校验：`HMAC_SECRET === 'change-me-before-deploy'` 或 `SIOT_PASS` 为默认值时，打印醒目警告并在"非演示模式"拒绝启动（或强制进入 dry-run 模式，与学生端对齐）；将默认值检出纳入质量门禁脚本。
